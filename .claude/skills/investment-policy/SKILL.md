# Investment Policy — 투자정책 작성 및 검토

$ARGUMENTS 를 바탕으로 투자정책서(IPS)를 작성·검토·개정한다. **이 Skill은 투자정책 수립을 지원할 뿐 승인·활성화·매매를 수행하지 않는다.**

## 필수 참조(순서)

1. `methodology/fund-management/architecture.md` — Research / Proposal / Approval 구분
2. `methodology/fund-management/investment-policy-template.md` — 정책 표준 양식
3. `methodology/fund-management/ips-quality-criteria.md` — 품질 5차원, G01–G12 차단 조건
4. `methodology/fund-management/ips-lifecycle.md` — 작성·검토·승인·개정 흐름
5. `research/phase1-1-investment-policy-methodology.md` — IPS 구성요소 연구 및 기관 사례

해당 참조가 없거나 상충되면 임의 기준을 생성하지 말고 **누락/충돌을 명시**한다. 기존 `portfolio-review` 또는 `position_plan.py`의 권장 비중을 승인된 정책으로 복사하지 않는다.

## 지원 작업

| 요청 | 작업 | 저장 가능한 산출물 |
| --- | --- | --- |
| `초안 작성` / `새 정책` | 사용자 목표와 제약 인터뷰 후 DRAFT 문서 생성 | `reports/policies/{policy_id}/draft-{date}.md` |
| `정책 검토 <파일>` | 기존 IPS의 누락·모순·검증 불가능 항목 평가 | `reports/policies/{policy_id}/review-{date}.md` |
| `정책 개정 <파일>` | 이전 정책을 보존한 채 차이·영향·개정 사유 정리 | `reports/policies/{policy_id}/revision-draft-{date}.md` |
| `상태 확인` | 보유 문서의 작성/승인 **기록 유무만** 확인 | 필요시 검토 요약 |

정책 ID는 파일 경로에 안전한 문자열로 정규화하고, 기존 파일에 무단 덮어쓰지 않는다. 파일을 저장하더라도 **승인된 ACTIVE 정책이 생성되는 것은 아니다**.

## 실행 절차

### 0. 기존 정책/참조 확인

- 사용자 입력의 `policy_id`, `portfolio_id`, 계좌 범위, 기존 정책 파일을 식별한다.
- 변경 요청이면 현재 정책과 이전 검토 이력을 읽는다. 기존 파일을 찾지 못하면 경로와 한계를 기록한다.
- 문서의 `ACTIVE` 문자열만으로 승인 효력을 추정하지 않는다. 결정론적 Validator와 연구용 Registry는 구현되어 있지만 **실제 사용자 인증과 운용 승격은 미구현/차단**되어 있다. 이번 Skill에서 ACTIVE를 인증할 수 없다.
- 개인정보, 계좌번호, 비밀번호, API 키 등의 상세 내용은 수집·보관하지 않는다.

### 1. 인터뷰: 이미 제공된 정보는 반복 질문하지 않는다

대화/문서에서 이미 확인된 값은 재사용한다. 빠진 핵심값만 물어보고, 답을 받지 못하더라도 **TBD가 명시된 초안**을 작성할 수 있다.

1. **적용 범위**: 연구용 모의 운용인가 실계좌인가? 포트폴리오/계좌 범위, 기준통화, 정책 소유자는?
2. **목적·기간**: 자산 성장/실질 구매력/현금흐름의 우선순위, 투자기간, 예정된 입출금·지급 의무는?
3. **수익·평가**: 필수 수익요구 vs 희망 수익, 벤치마크(통화·총수익·기간 포함)는?
4. **위험**: 재정적 **감수 능력(capacity)**과 심리적 **감수 의향(willingness)**을 구분할 자료는? 변동성·손실·유동성·레버리지 제한은?
5. **투자 가능 범위**: 자산군·시장, 금지 자산, 세금/계좌 제약, 환노출 원칙은?
6. **집중도·자산배분**: 종목/산업/국가 비중과 분모, SAA 목표 및 밴드는 정해졌는가? 정해지지 않았으면 Phase 2 입력으로 보류한다.
7. **거버넌스**: 사용자 승인, 리뷰 주기, 수정/중지 사유, 기록 보관 원칙은?

### 2. 초안 생성

- 반드시 `investment-policy-template.md`의 12개 정책 영역을 빠짐없이 반영한다.
- 확정되지 않은 필드는 `TBD`로 표기하고 **누가/무슨 근거로 결정해야 하는지** 적는다.
- 객관적 사실/사용자 선택/AI 제안/추정치의 출처를 구분한다.
- 정책의 최대 비중·수익률·MDD·자산배분 수치 등을 **AI가 임의 승인값으로 채우지 않는다**.
- `status: draft`, `approval: none`으로 표시한다. 정책 버전과 데이터 기준일을 명시한다.
- SAA 비중이 미정인 경우 Phase 2 결정 과제로 표시한다. 합계가 100%가 아니면 미완성 상태를 유지한다.
- AI는 투자 목표 간 상충관계를 설명하되 **투자자의 결정을 대신하지 않는다**.

### 3. 품질 진단

다섯 차원을 0–3점으로 **진단**한다.

| 차원 | 질문 |
| --- | --- |
| 완전성 | 운용 범위·목표·위험·기간·자산·승인 등 필수 정보가 있는가? |
| 일관성 | 위험, 유동성, 목적, 배분 제한이 충돌하지 않는가? |
| 실행 가능성 | 데이터와 책임자가 있어 실제 운영 가능한가? |
| 검증 가능성 | 숫자·기간·분모·조건을 코드로 검사할 수 있는가? |
| 재현성 | 정책 버전·승인·효력시점을 연결할 수 있는가? |

`G01–G12` 각 조건에 `PASS / FAIL / UNKNOWN`을 붙이고 근거를 적는다.

- **0–3점 합계가 높아도 검증 게이트 위반을 덮지 못한다.**
- 소스/기준일 불명, 정량 계산 불가능, 사용자 목표와 제약의 충돌은 `UNKNOWN`/검토 필요로 남긴다.
- 정성적 실현 가능성(G12)은 **사람의 판단이 필요**하다고 표시한다.
- 본 단계의 판정은 **AI 예비 진단**일 뿐, 현재 결정론적 검증의 `PASS`를 대신하지 않는다.

### 4. 정책 검토 및 변경 제안

기존 문서를 검토하거나 수정할 때:

- 기존 내용과 새 제안의 차이를 **필드 단위 이전/이후/변경 이유/위험 영향**으로 제시한다.
- 상위 제약을 완화(예: 종목 상한 증가)하면 추가 위험을 강조한다.
- 이미 발행된 정책 버전을 덮어쓰지 않고 **새 DRAFT**에 제안한다.
- 검토 결과가 양호하더라도 **정책 승인은 사용자 행위가 필요하다**.

### 5. 출력과 명시적 경고

출력 문서에 아래를 포함한다.

1. 정책 ID, 적용 범위, 상태 DRAFT, 버전, 작성일
2. IPS 12개 항목 및 미확정 항목 목록
3. 수익·위험 목표 간 충돌/가정/검증 근거
4. 품질 5차원 점수 및 G01–G12 예비 판정
5. 결정이 필요한 항목·담당자·후속 검토 권고
6. 정책 승인·활성화·주문은 수행하지 않았다는 고지

마지막 상태 줄은 반드시 다음처럼 작성한다.

> **정책 상태: DRAFT (미승인) | 자동 투자 승인: 불가 | 실제 주문: 수행하지 않음**

### 6. 절대 금지

- AI 출력으로 `ACTIVE` 정책을 만들거나 기존 ACTIVE를 바꾸기.
- 정책의 위반·미정 값을 추정해서 `PASS` 처리.
- `investment-research`의 `매수` 판단을 승인 또는 실제 매수로 취급.
- `decision-ledger`를 정책 승인 원장으로 취급.
- 기존 보고서 파서의 `**판단**`, `**실행 계획**`, `## 실행 정보` 라벨을 수정.
- 사용자 명시 승인 없이 정책 효력 시작·중지·예외를 확정.

## 연동 및 테스트 참고

현재 도구의 입력 계약은 `methodology/fund-management/policy-gate-implementation.md`, 등록 경계는 `methodology/fund-management/policy-registry-integrity.md`, 시나리오는 `methodology/fund-management/policy-workflow-validation.md`를 참조한다.

- Markdown IPS를 Validator가 직접 읽는 것으로 가정하지 않는다. 사용자 확인값을 JSON으로 옮길 때 출처를 유지하고 미정 값은 누락/TBD로 남긴다. 검사 통과를 위해 승인자·승인시각·사람 검토·자료 출처를 생성하거나 draft를 active로 바꾸지 않는다.
- JSON이 준비되면 `python3 ~/ai-berkshire/tools/policy_validator.py policy --policy <정책.json>`으로 검사하고 종료 코드(0/2), `result`, `errors`, `gates`, `scope`, `approval_granted`를 기록한다. PASS는 기계적 계약 통과이며 사람의 승인이나 외부 자료 인증이 아니다.
- 결과에 **자료/정책 보완 필요**(누락 필드·자료·배분 모순 등)와 **사용자 결정/승인 필요**(한도 선택·G12 판단·승인 기록 등)를 별도 항목으로 적는다. 둘은 동시에 해당할 수 있다. G01/G09 같은 게이트에도 여러 원인이 있으므로 번호만으로 분류하지 말고 실제 오류를 인용한다. `approval_granted=false`는 어떤 경우에도 유지한다.
- 일반 Skill 실행에서는 Registry 등록을 호출하지 않는다. 합성 통합 테스트만 별도 임시 디렉터리에서 `--research-only`와 고유 `event_id`를 사용한다. 반환된 `research_active`는 운용 정책이 아니며 제안 검증에서도 차단되어야 한다. 실제 사용자 정책이나 승인 이벤트를 합성하지 않는다.
- 기존 연구 Registry의 상태 조회는 `show`/`audit`로 수행한다. 사본 불일치가 있으면 원인·복구 필요를 보고한다. `active.json` 파일명만으로 ACTIVE를 추정하지 않는다.
- 제안의 기계적 검사에는 `python3 ~/ai-berkshire/tools/policy_validator.py proposal --policy <정책.json> --portfolio <스냅샷.json> --proposal <제안.json>`을 사용한다. 정책 버전·스냅샷 불일치나 DRAFT 차단을 우회하지 않는다.
- Python 계약 테스트, Work CLI 실행, 실제 Claude Skill 실행의 결과를 구분한다. CLI 통과를 Skill 런타임 검증 완료로 기록하지 않는다.

확인할 대표 사례: 미확정 투자기간, 목표 비중 합계 오류, 종목 비중 분모 누락, 정책 리스크 한도와 `position_plan.py` 10% 기본값 충돌, 무단 ACTIVE 선언, 기존 보고서 라벨 유지.
